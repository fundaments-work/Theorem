# v1.1 Roadmap — Best-in-Class Open-Source Ebook Reader

## North Star

Theorem is a **local-first ebook reader** that owns the core reading experience deeply. Not a read-it-later platform, not a PKM hub. Every feature must justify itself against: *"Does this make reading better?"*

## Guiding Principles

- **No feature bloat** — every addition must serve the core reading experience
- **Mobile matters** — Android is a first-class platform; tablet UX is a priority
- **Performance is a feature** — cold start, page turns, and sync must feel instant
- **Local-first** — no cloud dependency, no account, no vendor lock-in

## Immediate Priorities (Sprints 1-3)

### Sprint 1: Cold Start Optimization

| Metric | Current | Target |
|--------|---------|--------|
| First paint | ~3s | <500ms |
| Full interactive | ~4s | ~1.5s |
| FTS re-index on 1K books | ~500ms per start | ~10ms (skip if unchanged) |

**Changes:**

1. **Skip FTS re-index when unchanged** — Store a hash of the books array content. If unchanged since last FTS write, skip the `sqliteIndexBooksFtsBatch` call entirely. This saves 500ms-2s on every app start.

2. **Fire-and-forget cover restoration** — Instead of sequential batched SQLite reads before first render, start rendering the library immediately with placeholder covers. Restore covers via `requestIdleCallback`. First paint drops from ~3s to <500ms.

3. **Defer sync bootstrap** — `ensureResponderSyncReady()` currently blocks the startup critical path. Move `irohStart()` to after first render. The user sees the library immediately; sync initializes in the background.

4. **Lazy library store deserialization** — Split the Zustand library store so `books` array is loaded separately from the rest of the UI state. The shell (sidebar, titlebar, settings) renders without waiting for the full book list to deserialize.

**Files touched:** `src/App.tsx`, `src/core/store/libraryStore.ts`, `src/core/lib/sync-orchestrator.ts`, `src-tauri/src/database.rs`

### Sprint 2: OPDS Catalog Browsing

Browse, discover, and import books from OPDS catalogs.

**Scope:**
- New route/panel in the library for OPDS catalogs
- Add catalog URL (text input + presets for Gutenberg, Standard Ebooks)
- Fetch and parse OPDS 1.2 Atom feed (title, author, cover, description, download links)
- Browse navigation feeds hierarchically
- Search within catalogs (OpenSearch integration)
- One-tap download EPUB → import into library

**OPDS 1.2 spec summary:**
- Atom XML with Dublin Core metadata
- Navigation feeds (browse hierarchy) + Acquisition feeds (downloadable books)
- Relations: `http://opds-spec.org/acquisition` for download, `http://opds-spec.org/image` for cover
- OpenSearch for catalog search
- Facets for filtering (category, language, etc.)
- Pagination via RFC 5005

**Security:** Only HTTPS URLs. No credential storage (user provides them per-session or we use system keychain).

**Files to create:** `src/features/library/OPDSBrowser.tsx`, `src/core/lib/opds.ts`
**Backend:** No Rust changes needed (fetch via existing Tauri HTTP plugin or direct fetch)

### Sprint 3: Reading Goal Notifications + Annotations Performance

**Reading Goal Notifications:**

Use `tauri-plugin-notification` for native system notifications.

- Tauri plugin already supports: Linux, macOS, Windows, Android
- Permission flow: `isPermissionGranted()` → `requestPermission()` → `sendNotification()`
- Rust-side scheduling via a timer that checks daily goal progress at configurable times
- Notification: "You're X min short of your daily reading goal — keep going!"
- Clicking notification opens Theorem to the library (or resumes last book)

**Files touched:** `src-tauri/Cargo.toml` (add `tauri-plugin-notification`), Rust timer command

**Annotations O(n) → Map:**

The reader event handlers currently use `annotations.find(callback)` which is O(n) per interaction. With thousands of annotations, this causes frame drops during tap/highlight operations.

- Build `annotationsByCfi: Map<string, Annotation>` lookup when opening a book
- Replace all `annotations.find()` calls in `Reader.tsx` event handlers with map lookups
- ~1 day of work, prevents a scalability issue

## Medium-Term (Sprints 4-5)

### Sprint 4: Split-Screen (Parallel Reading)

Desktop + tablet only. Two books side by side.

**UX:**
- "Split" button in reader toolbar opens a second reader panel
- Each panel is an independent `ReaderViewport` instance
- Independent scroll/position per panel
- Optional synchronized scrolling (toggle)
- Resizable divider between panels
- On tablet: landscape orientation triggers split automatically

**Backend changes:** Reader state needs to support multiple active sessions (`activeBookIds: string[]` instead of `currentBookId: string`). The store already has per-book position tracking, so this is mostly a UI lift.

**Design questions to resolve:**
- How does TTS interact with split-screen? (disable TTS during split)
- How does annotation selection work across panels?
- Should search search all open books or just the active panel?

---

### Sprint 5: Sync

*Requires ongoing research — see open questions below.*

**Objective:** Make sync work reliably across different networks, during travel, and without both devices needing to be online simultaneously.

**Options under research:**

| Approach | Pro | Con |
|----------|-----|-----|
| File-based (Syncthing) | Truly offline, no server, local-first | Requires external tool, LWW conflicts |
| Cloud plugin (S3/WebDAV) | Works everywhere, simple UX | Server cost, local-first trade-off |
| iroh relay server | Keeps current architecture | Both devices must be online, relay infra |

---

## Out of Scope

- iOS (no Apple devices to develop on)
- Web clipper browser extension (read-it-later territory, not core reading)
- Newsletter email inbox (requires email server infrastructure)
- Audiobooks (different UX paradigm, would dilute focus)
- Plugin system (KOReader's approach — valuable but very high effort)
- E-ink optimization (niche hardware, not the target platform)

---

## Open Questions for Sync Research

1. Can iroh work reliably across the internet with a self-hosted relay? What's the latency?
2. File-based sync: encrypted SQLite dump or individual JSON files?
3. How does last-write-wins conflict resolution compare to CRDT for reading progress + annotations?
4. Should we use a hybrid: P2P for LAN (existing) + file-based for WAN?

Decision target: Before Sprint 5 begins.
